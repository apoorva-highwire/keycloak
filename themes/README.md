# HighWire Keycloak themes

## Structure

```
themes/
  hw-base/
    login/                             — shared base login theme, all publishers inherit from this
      theme.properties                 — parent=keycloak, declares css/login.css, locales=en
      login.ftl                        — username/password + institution SSO link
      register.ftl                     — registration + optional per-client T&Cs link
      login-reset-password.ftl         — "forgot password"
      login-update-password.ftl        — forced password change
      login-otp.ftl                    — one-time code entry (2FA)
      select-authenticator.ftl         — choose between multiple configured login methods
      login-verify-email.ftl           — email verification prompt
      idp-review-user-profile.ftl      — profile confirmation on first brokered-IdP login
      terms.ftl                        — realm-wide Terms & Conditions required action
      logout-confirm.ftl               — "are you sure you want to log out"
      error.ftl / info.ftl             — standard Keycloak error/info pages, HighWire-styled
      messages/messages_en.properties  — HighWire-specific message keys
      resources/css/login.css          — every visual choice as a CSS custom property (--hw-*)
      resources/img/favicon.ico, highwirepress-logo.svg  — default favicon + logo
      resources/fonts/                 — drop self-hosted font files here if needed
    account/                           — User Account Console theme (CSS-only, see § below)
      theme.properties                 — parent=keycloak.v3, declares css/account.css
      resources/css/account.css        — same --hw-* token names as the login theme
    admin/                             — Admin Console theme — staff-only, NOT per-publisher
      theme.properties                 — parent=keycloak.v2, declares css/admin.css
      resources/css/admin.css          — same --hw-* token names again
    email/                             — branded wrapper for every email Keycloak sends
      theme.properties                 — parent=keycloak, only html/template.ftl is overridden
      html/template.ftl                — the emailLayout macro: header/logo/footer, literal hex colors
      messages/messages_en.properties  — hwEmailFooter text
      resources/img/highwirepress-logo.svg
  bmj/                                  — a real publisher theme, generated by scripts/new-publisher-realm.sh
    login/
      theme.properties                 — parent=hw-base, loads login.css then publisher-overrides.css
      resources/css/publisher-overrides.css  — redefines only the --hw-* variables that differ
      resources/img/logo.svg           — drop the publisher's logo here (referenced by --hw-logo-url)
    account/
      theme.properties                 — parent=hw-base, loads account.css then publisher-overrides.css
      resources/css/publisher-overrides.css  — mirrors the login one (see note in the file)
    email/
      theme.properties                 — parent=hw-base
      html/template.ftl                — full duplicate of hw-base's, literal colors changed (see § below)
      resources/img/logo.svg           — drop the publisher's logo here too (separate copy, see note)
```

Note what's **missing** from every publisher theme on purpose: no `admin/` folder. The admin console is
staff-only (`highwire-admin` realm, separate from every publisher realm per
`PUBLISHER-ADMIN-PANEL.md` §2a) — publishers never see it, so there's exactly one shared admin theme
(`hw-base`, assigned directly — no per-realm wrapper folder), not one per publisher.

Every page is a real, working override of Keycloak's base login theme pages (they
`<#import "template.ftl" as layout>` and inherit the base theme's layout/chrome via `parent=keycloak` —
only the content and HighWire-specific additions are custom). A publisher theme never needs to copy any
`.ftl` file — only CSS variables and a logo, since `parent=hw-base` inherits every page automatically.

Library card and voucher redemption were removed from the login screen (and their scaffold pages
deleted) — only username/password and institution SSO remain as login options. If either is needed
again later, it would need a custom Authenticator SPI first (see `AUTH-AUTHZ-KEYCLOAK-MAPPING.md` Part 1,
auth types #7/#8, and `NEW-AUTH-AUTHZ-KEYCLOAK-PLAN.md` §2) — Keycloak has no native credential type for
either.

## Adding a new publisher theme

One command does all of it — realm, roles, AND the theme folder:

```
./scripts/new-publisher-realm.sh acme-press "Acme Press"
```

This generates `themes/acme-press/` (parent=hw-base throughout, same shape as `themes/bmj/`), with
every `--hw-*` value starting at hw-base's own defaults (clearly "not customized yet", not an arbitrary
example palette), and imports the realm itself (reader/author/reviewer/editor/publisher-admin roles,
`reader-app` client) via `scripts/realms/publisher-template.json`. What's left manually:

1. Edit `themes/acme-press/login/resources/css/publisher-overrides.css` **and**
   `themes/acme-press/account/resources/css/publisher-overrides.css` with the real brand values —
   change only the variable values, don't touch selectors, and keep the two files in sync (Keycloak
   resolves login/account theme resources separately, so this is a deliberate duplication, not a bug).
2. Replace `themes/acme-press/login/resources/img/logo.svg` with the publisher's real logo.
3. Restart the `keycloak` container so the new theme folder is picked up (local dev: themes are
   bind-mounted, so a restart is enough, no rebuild — `docker compose restart keycloak`).

The realm's `loginTheme`/`accountTheme` are already set to `acme-press` by the import — no manual
Realm Settings → Themes step needed, unlike the old copy-by-hand workflow this replaced.

## Account console — CSS-only

Keycloak 26's default User Account Console (`keycloak.v3`) is a built React SPA, not FreeMarker
templates like the login theme — there's nothing equivalent to `login.ftl` to override. Branding is
CSS-only via `account/resources/css/account.css`, reusing the same `--hw-*` token names as the login
theme so one mental model covers both.

## Admin console — CSS-only, one shared theme, no publisher variants

Same situation as the account console (`keycloak.v2`, a React SPA, CSS-only branding via
`admin/resources/css/admin.css`) — except there is deliberately **no per-publisher admin theme at
all**. The `highwire-admin` realm's `adminTheme` is set directly to `hw-base` in
`scripts/realms/highwire-admin.json` — no `highwire-admin/` theme folder wrapping it; that thin
wrapper (just a `theme.properties` with `parent=hw-base` and nothing else) was removed as pure
indirection once it was clear nothing else needed to live in it.

## Email theme — the one place CSS variables don't work

Every email Keycloak sends (password reset, email verification, the admin console's "Test connection"
button, identity-provider link confirmations, etc.) is a FreeMarker template under `email/html/` and
`email/text/`. Rather than re-authoring each one, `hw-base/email/html/template.ftl` overrides only the
shared `emailLayout` macro every content template renders through — branding (header bar, logo, footer)
applies automatically to all of them via theme inheritance, same principle as the login theme's
"override chrome, not content" approach.

The one real difference: **email HTML can't reliably use CSS custom properties** — most email clients
(Outlook desktop especially) strip `<style>` blocks using `var()`, so every color in
`email/html/template.ftl` is a literal hex value, not a `--hw-*` token. A publisher email theme
therefore has to **copy the whole template file** and change the literal values directly (see
`bmj/email/html/template.ftl` for a real example) if it needs different email branding than hw-base's
own — `scripts/new-publisher-realm.sh` doesn't generate this file at all by default (just a
`theme.properties` inheriting hw-base's unchanged), since most publishers don't need to touch it.
`email/resources/img/` is also a separate resource path from `login/resources/img/` — the logo has to
be dropped in both places per publisher, if the email template is customized.

`email/text/template.ftl` is **not** overridden anywhere — plain-text emails have no branding surface,
so Keycloak's own pass-through default is already correct.

Once the IAM service (`MULTI-TENANT-KEYCLOAK-IAM-PLAN.md` §6) exists, the generated
`publisher-overrides.css` becomes something IAM templates server-side from values stored in Postgres,
rather than a file hand-edited per publisher — `scripts/new-publisher-realm.sh` is the interim,
file-based version of that same provisioning step.

## Running locally

```
cd hosting-new/keycloak/docker
docker compose up -d
```

Admin console: http://localhost:8081 (`admin` / `admin`, from `docker-compose.yml`'s
`KEYCLOAK_ADMIN`/`KEYCLOAK_ADMIN_PASSWORD` — change both before this ever points at anything real).

Theme edits under `themes/` take effect on `docker compose restart keycloak` — no rebuild needed, since
`docker-compose.yml` bind-mounts the directory over the image built by `Dockerfile`. Drop the mount (and
just run the image `Dockerfile` builds) for any shared/deployed environment.
